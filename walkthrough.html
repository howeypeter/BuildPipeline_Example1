1. Developer Experience & Local Toolchain

Modeled on modern platform engineering principles, the build pipeline is designed as an accelerator, not a roadblock. The goal is to maximize developer velocity by providing a seamless local toolchain with automated guardrails. Quality, security, and packaging guarantees run automatically so product teams can focus on customer features with total confidence.

Platform Accelerator: Multi-Service Workspace
The workspace automatically discovers any directory matching app* or svc* containing a main.py (such as primary service app/ and telemetry sidecar svc_sidecar/). Developers can build, test, and package single microservices or the entire fleet using identical, zero-boilerplate commands.

Local Developer Workflow

STEP 01 Setup Isolated Virtual Environment

Creates an isolated Python 3.12 environment in app/.venv matching the container base image:

make venv

STEP 02 One Command Fast Local Validation

Runs code formatting, Ruff static linting, and all tests across every microservice simultaneously in under 2 seconds:

make validate SERVICE=all

STEP 03 Target Specific Service Test Suites

Isolate tests to a specific application or sidecar without executing unrelated suites:

make test SERVICE=app
make test SERVICE=svc_sidecar

STEP 04 Advisory AI Code Quality Review

Runs non-blocking AI consistency recommendations without causing pipeline friction or build failures:

make lint-ai

STEP 05 Local Hardened Container Packaging & Smoke Check

Builds container images using ARG SERVICE_DIR and validates user 65532:65532, healthchecks, and read-only execution locally:

make docker-build SERVICE=app
make docker-run SERVICE=app

make docker-build SERVICE=svc_sidecar
make docker-run SERVICE=svc_sidecar

Developer Platform Standard: Structured JSON Logging

Unstructured text logs break centralized log query aggregators (such as CloudWatch, Datadog, or Elastic). Microservices automatically emit single line JSON records conforming to platform standards:

{
  "timestamp": "2026-11-08T05:31:55.123456+00:00",
  "level": "INFO",
  "logger": "app",
  "service": "app",
  "message": "handled request",
  "method": "POST",
  "path": "/items",
  "status": 201,
  "duration_ms": 1.45,
  "client_ip": "127.0.0.1",
  "request_id": "a17f2231-155e-42ab-9cf0-df8efbc2a2ee"
}

Required platform keys include ISO 8601 UTC timestamp, uppercase level, registered service, correlation request_id, and latency duration_ms.

Developer Platform Standard: API Interface Contract

To integrate cleanly with service meshes, API gateways, and client SDK generators, every service conforms to standard interface rules:

  • OpenAPI Contract Serving: Exposes its machine-readable schema on GET /openapi.json.
  • Semantic Validation Status: Returns 422 Unprocessable Entity for invalid input payloads, rejecting malformed data with structured error bodies.
  • Probe Separation: Distinct separation between liveness (/healthz) and traffic readiness (/readyz).
  • Correlation ID Tracking: Accepts incoming X-Request-ID or generates a UUID, propagating it through headers and structured logs.

3. Automated Build Pipeline & Embedded Gateway Standards

The delivery pipeline validates every commit, automatically enforcing standards established across InfoSec, Platform, Reliability, and QA domains. Rather than creating roadblocks or manual approval queues, these gateways are instrumented directly into the automated paved path.

InfoSec Gateway Standards

Standards Authority: Information Security (SecOps)

Gate 1: Snyk Open Source (SCA)

Scans dependencies prior to compilation against vulnerability databases. Automatically fails builds on High or Critical severity flaws.

Gate 2: Snyk Container

Scans the assembled container layers, OS libraries, and system binaries. Enforces zero High or Critical vulnerabilities before admission.

Platform & Supply Chain Standards

Standards Authority: Developer Platform Architecture

4. Upstream Platform Inheritance: The 90/10 Architecture

Developers should never have to manually construct hundreds of lines of Kubernetes YAML or Helm boilerplate. The 90%+ platform defaults are built by an upstream process and inherited automatically.

Upstream Chart Architecture

A centralized platform engineering pipeline builds, hardens, and publishes the official standard service Helm chart as a versioned package. When product teams launch a microservice, they simply reference the upstream chart as a dependency.

Zero Boilerplate for Developers
Developers do not need to specify "Use port 8000", configure liveness probe paths, or define security contexts. All of the following are inherited platform defaults:
  • Port 8000: Pre-configured across container, Kubernetes Service, and Ingress routing.
  • Hardened Security Context: Numeric unprivileged user 65532:65532, dropped Linux capabilities, and read-only root filesystem.
  • Health Probes Wiring: Liveness (/healthz) and readiness (/readyz) automatically wired with socket draining delays.
  • Horizontal Pod Autoscaling (HPA): Compute scaling policies pre-configured.
Autoscaling Principle: Why We Never Scale on Memory
Autoscaling must always be driven by CPU utilization, request volume, or queue depth (such as SQS or Kafka via KEDA). Autoscaling must never scale on memory because language runtimes (Python, Java, Node) retain allocated memory and cached buffers, which prevents downscaling and leads to scaling thrashing.

What the Developer Actually Writes

The product developer repository contains only the minimal 10% configuration:

5. Reliability Gateway, Health Probes & Socket Draining

A production-ready service coordinates with Kubernetes ingress, AWS Target Groups, and orchestrator signals to guarantee zero dropped requests during rolling upgrades and spot node evacuations.

How /readyz Enables Graceful Socket Draining

During rolling deployments or AWS Spot terminations, Kubernetes sends a SIGTERM signal to the container. To prevent dropped connections:

  1. Readiness Flips to 503: The service marks is_ready = False. The next probe to /readyz returns 503.
  2. Traffic Withdrawn: The upstream load balancer stops routing new requests to this pod replica.
  3. Socket Draining: The server keeps listening to allow active in-flight requests to complete cleanly.
  4. Clean Termination: Once active requests reach zero, the server closes listener sockets and exits with code 0.

Promotion & Zero-Rebuild Rollbacks

Build Once, Promote Everywhere

The CI pipeline builds the container image once from the Git commit SHA. That identical container image is promoted across environments (Dev, Staging, Production). Only environment variables and secrets change between environments.

Instant Rollback Mechanism

If an issue occurs in production, never trigger a rebuild. Rollback is executed by updating the Kubernetes deployment manifest (ArgoCD Application, Flux, or Helm release) to point to the previous immutable Git SHA tag (such as :sha-previous). Because the image is cached in the registry, rollbacks complete in seconds.
